# Contributing to AzCmply

Bug reports, wrong results, new tests, framework mappings, documentation and web page fixes are all welcome.

- Something breaks: open a **Bug report**.
- A test reports the wrong result: open a **Wrong test result**, with the test id.
- A check or mapping is missing: open a **New test or framework mapping**.
- Anything else: open a **Feature request**.
- A vulnerability in AzCmply itself: do not open an issue, see [SECURITY.md](SECURITY.md).

For more than a small fix, open an issue first, so we can agree on the approach before you build it.

## How the repository fits together

| Folder | What it holds |
|---|---|
| `Ingest` | `Invoke-AzureIngest.ps1`: collects a subscription, read only, into a folder of JSON files |
| `Analyze` | `Invoke-AzureAnalyze.ps1`, the tests (`tests\NN-Area.ps1`), shared helpers (`lib\AnalyzeCore.ps1`), the framework catalogs (`catalog\frameworks`) and the self-test (`selftest`) |
| `Report` | `New-AzureSecurityReport.ps1`: the HTML report |
| `PSModule` | The PowerShell module, generated by `Build-AzCmplyModule.ps1` at release. Do not edit it. |
| `Web` | AzCmply web. `Web\site\generated` is converted from the PowerShell source by `Web\Convert-AzCmplyToWeb.ps1`; do not edit it. `Web\site\js\ingest.js` is the browser version of the ingestion, kept in step by hand. |

The PowerShell is the only place where tests, analysis, comparison and report are written; the browser runs code generated from it.

## What you need

- PowerShell 7.2 or later (7.5 recommended).
- Node.js 20 or later, for the web checks.
- No Azure subscription for most work: the self-test runs every test against two synthetic ingestions.

To collect a real subscription you need a service principal with **Reader** on the subscription and the Microsoft Graph application permission **Directory.Read.All** (see the [README](README.md)). The live comparison of the two ingestions reads it from `Ingest\creds.local`, which git ignores:

```
appid: <application id>
tenantid: <tenant id>
secret: <client secret>
subscriptionid: <subscription id>
```

## Rules that keep the results honest

Breaking these makes AzCmply state something untrue, so pull requests are checked against them.

- **Read only.** No write calls, and no data that needs more than Reader (listing keys, app settings, data plane content).
- **Pass and Fail only on data that was read.** Declare the ingestion sections a test needs in `Requires` and check child resources with `Test-ChildCollected`; report `New-Unknown` with the reason when data is missing. The self-test removes each ingestion file in turn and fails any test that then passes.
- **Deterministic output.** Sort with a tie breaker, and never depend on the order of an unordered hashtable.
- **No secrets in evidence.** Name the setting and where it is, never the value.
- **One requirement per test**, and no test that checks the same setting on the same resource as another test.
- **Frameworks are peers.** Each has its own catalog in `Analyze\catalog\frameworks`, and every test evidences at least one control there. A control only lists tests that address what it asks. AzCmply Custom holds JSolve's own controls for Azure attack paths that no other framework covers.
- **Plain, short text.** Titles state the requirement; descriptions say what is checked, rationales why, remediations how. No marketing language, and no em dash character.

`AGENTS.md` has the full set, including the rules for the web page.

## Adding or changing a test

1. **Write the test** in the file of its area in `Analyze\tests`, with `Add-AzTest`. Use the next free id of the area (`AZ-STG-028`), or a new area code for a new service. Required fields: `Id`, `Title`, `Category`, `Service`, `Severity`, `Description`, `Rationale`, `Remediation`. Add `References`, and `Defender` and `Policy` ids only when you verified them against Microsoft's published definitions.
2. **Evaluate per resource** with `ResourceTypes` (and a `Filter` if needed) and an `Evaluate` block that returns `New-Pass`, `New-Fail`, `New-Unknown` or `New-NotApplicable` with a detail and evidence. Use `Run` for subscription level checks.
3. **Changing the logic of an existing test?** Increase its `Version`, so a comparison between runs shows that the logic changed.
4. **Map it** in every framework catalog whose controls it evidences: add the id to the `tests` list of the control, in sorted order. Attack paths no framework covers go to AzCmply Custom (`azcmply-custom.json`), whose `version` goes up when its controls change.
5. **Cover it in the fixture.** `Analyze\selftest\New-FixtureIngest.ps1` builds a compliant (`Good`) and a non-compliant (`Bad`) ingestion. Make the test pass on the first and fail on the second. When one fixture cannot do both, add an expected status to `Invoke-SelfTest.ps1` with the reason.
6. **Run the checks:**

   ```powershell
   .\Analyze\selftest\Invoke-SelfTest.ps1                # every test, both fixtures, degraded ingestions (a few minutes)
   .\Web\Convert-AzCmplyToWeb.ps1                        # regenerate the web variant
   .\Web\generator\Test-WebParity.ps1 -Thorough          # browser and PowerShell give the same output
   ```

   To try one test quickly:

   ```powershell
   .\Analyze\selftest\New-FixtureIngest.ps1 -Path $env:TEMP\fixture-Bad -Mode Bad
   .\Analyze\Invoke-AzureAnalyze.ps1 -IngestPath $env:TEMP\fixture-Bad -OutputPath $env:TEMP\results -TestId 'AZ-STG-028'
   ```

   If the converter stops on a PowerShell construct, say so in the pull request; the converter or its runtime may need to learn it.
7. **Update the documentation:** the test counts in `README.md` and `Analyze\README.md`, and an entry in `CHANGELOG.md`.

## Collecting more data

- What is collected is data in the `#region collection maps` of `Ingest\Invoke-AzureIngest.ps1`: child resources per type, subscription endpoints, metrics. Keep that region literal data; the generator hands it to the browser as is.
- A change to how data is collected (not only what) needs the same change in `Web\site\js\ingest.js`. With a subscription, verify both with `Web\generator\Test-WebIngestParity.ps1`.
- Describe new output in `Ingest\README.md`.

## Web page changes

The page keeps a strict Content Security Policy: no third party scripts, styles or fonts, no inline scripts except those whose hashes the converter stamps, and text set with `textContent`, never `innerHTML` with data. Run `Web\Convert-AzCmplyToWeb.ps1` after every change, and check the page with `Web\Start-AzCmplyWeb.ps1` and `Web\generator\page-check.mjs` at 1280 and 390 pixels wide.

## Pull requests

- Branch from `main`, keep one topic per pull request and link the issue.
- Leave `VERSION` alone: the maintainer sets it at release, and a new version on `main` publishes the module. Add your changelog entry under `## Unreleased` at the top of `CHANGELOG.md`.
- Never commit ingestion folders, results, reports or `creds.local`. They describe real weaknesses of a tenant.
- GitHub runs the self-test, checks that the generated web files match the source and runs the web parity check on every pull request.
